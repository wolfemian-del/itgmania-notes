2. Code string syntax (as parsed on beta) [CODE: InputQueue.cpp
   InputQueueCode::Load / ParseCodeString]
   - "|" separates ALTERNATIVE patterns. Any one matching fires the code.
   - "," separates successive presses in a sequence ("Up,Up").
   - "-" joins buttons pressed together in one step (all must be pressed
     within 0.05 s of each other: g_fSimultaneousThreshold).
   - Prefixes on a button name: "@" must be held when the press happens;
     "!" must NOT be held; "+" also accepts key-repeat events; "~" fires
     on release instead of first press. Prefixes can stack.
   - Time window per pattern: 0.55 s for a 1-step pattern, else
     (steps-1) x 0.6 s. (Same numbers as v1.3.0; now computed per
     alternative instead of stored on the object.)
   - Example from the fallback theme: "Up-Down|@MenuDown-MenuUp" =
     Up+Down together, OR press MenuUp while holding MenuDown.
   Whether "!" / "~" behave as described was read, not tested.
 
3. What "|" changes [CODE: diff of a657f14ed7]
   - Load() splits on "|" (empty pieces ignored) and parses each piece
     separately into m_aPatterns.
   - EnteredCode() tries each pattern; on the first match it clears the
     controller's input queue and returns true. (v1.3.0 cleared the
     queue inside the single-pattern matcher; same net effect.)
   - Parse failures are per-alternative: an alternative with an unknown
     button name is DROPPED (Trace log only) and the others still load.
     Load() returns false only if NO alternative parsed. In v1.3.0 any
     bad button made the whole code fail. [CODE]
     Consequence [INFERRED]: a typo in one alternative fails quietly.
   - A string without "|" behaves as before, apart from the above.
   - Applies everywhere InputQueueCode is used: CodeDetector metrics
     ([CodeDetector], [CourseCodeDetector] etc.), and InputQueueCodeSet
     (CodeSet.cpp), which loads [<Screen>] CodeNames/Code<Name> metrics
     and OptionsList codes. [CODE: CodeSet.cpp, Screen.h, OptionsList.h]
   - Motivation per commit message: avoid needing NextSort1/2/3/4-style
     duplicate code slots. The existing numbered slots are unchanged.
 
4. Close-folder fallback [CODE: Themes/_fallback/Scripts/03 Gameplay.lua
   ~344-348, beta]
     CloseCurrentFolder default = "MenuUp-MenuDown"            (unchanged)
     dance = "Up-Down|@MenuDown-MenuUp"     (was "Up-Down" in v1.3.0)
     pump  = "@UpLeft-@UpRight-Center|@MenuDown-MenuUp"
   So on beta, dance and pump gain "hold MenuDown, press MenuUp" as a
   second way to close the current folder/series level. The default
   (other games) still uses simultaneous MenuUp+MenuDown.
   Effect on the wheel: CloseOpenSectionOneLevel(), one level at a time
   (see series notes section 5). [CODE]
 
   Order change in ScreenSelectMusic::DetectCodes: EnteredCloseFolder is
   now tested before PrevSteps/NextSteps. The code comment says the
   fallback command is a prefix of the prev/next steps command.
   Checked why [CODE for SL metrics; INFERRED for the reason]: Simply
   Love's [CodeDetector] sets PrevSteps2="MenuUp" and NextSteps2=
   "MenuDown" (single presses). The fallback's final press, MenuUp, also
   satisfies PrevSteps2, so without the reorder a close-folder gesture
   could also change steps (whichever is tested first wins, and the
   winner clears the queue). The fallback theme's own PrevSteps2 is
   "MenuUp,MenuUp", which is a weaker overlap.
   Simply Love uses GetCodeForGame("CloseCurrentFolder"), so it inherits
   the new fallback value. [CODE: Simply Love metrics.ini ~1735]
   Not in v1.3.0.

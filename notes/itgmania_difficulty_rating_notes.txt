-------------------

   formula would want, cached in the song cache file: radar values, tech
   counts, notes-per-measure, NPS-per-measure, peak NPS. Nothing new has to
   be parsed at song select. [CODE]

   Steps::CalculateStepStats (Steps.cpp ~324): GetNoteData, then

c) A "predict the meter from radar values" function ALREADY EXISTS:
   Steps::PredictMeter (Steps.cpp ~263). Details in 2. [CODE]
d) The step-parity analysis already computes a cheapest-path total cost for
   the whole chart (endNode->totalCost, StepParityGenerator.cpp ~109) and
   discards it; only the derived TechCounts are kept. That cost is a

2. EXISTING PredictMeter (Steps.cpp ~263-286) [CODE]
   meter = 0.775
         + 10.1*Stream + 5.27*Voltage - 0.905*Air - 1.10*Freeze + 2.86*Chaos
         + difficulty offset (Beginner/Easy -0.877, Hard/Challenge +0.722,
           Medium and Edit 0)
         - 6.35*(Stream*Voltage) - 2.58*(Chaos^2); floor 1.
   Only the first five radar categories carry coefficients (array of 13 for
   14 categories, last zeroed). Uses PLAYER_1 radar values.
   Callers: Steps::TidyUpData sets the meter to int(PredictMeter()) ONLY when
   the file's meter is < 1; ScreenEdit.cpp ~5321 shows it; Lua
   Steps:PredictMeter(). It uses the DDR-style radar (0-1 scale values, see
   3), so it is a legacy 1-10-era predictor; it has no tech/footwork input
   and no 1-20 calibration [INFERRED from the coefficients; not evaluated
   against real charts]. It depends on the chart's own Difficulty label, so
   it is not label-free.
   ADDENDUM 2026-10-10 [CODE, plus arithmetic run on INVENTED inputs]:
   - Units: Stream = (taps/s)/7; Voltage = (peak notes in an 8-beat window
     / 8 x average beats/s)/10. The radar calculation does not clamp
     (NoteDataUtil.cpp ~1022-1033), so a chart averaging more than 7
     notes/s gives Stream > 1.
   - The -6.35*Stream*Voltage term makes the formula NON-MONOTONE:
     d(meter)/d(Stream) = 10.1 - 6.35*Voltage = 3.75 at Voltage 1.0 and
     negative above Voltage 1.59. Invented inputs: (S .25, V .25, Medium)
     = 4.3; (S .5, V .5, Hard) = 7.7; (S 1, V 1, Challenge) = 10.9;
     (S 1.5, V 1.5, Challenge) = 10.7. It saturates near 11, so it cannot
     rank modern dense charts. Its int() cast truncates (10.9 -> 10).
   - The difficulty-label offsets mean it partly echoes the chart's own
     label, which makes it unsuitable as an independent estimate.
   - Provenance: git log -S"0.775f" reaches only the import commit
     "smsvn -> ssc-hg glue"; what data the coefficients were fitted on
     cannot be recovered from this repository.
 
3. WHAT THE CACHED FEATURES ARE (and their limits)
--------------------------------------------------
RadarValues (NoteDataUtil.cpp ~905-1037) [CODE]
  Stream  = (taps / song seconds) / 7
  Voltage = (peak notes in an 8-beat window / 8) * (lastBeat/songSeconds) / 10
            (uses the average BPS, not the timing data)
  Air     = jumps / song seconds;  Freeze = holds / song seconds
  Chaos   = rows of 12th-note-or-finer / song seconds * 0.5
  plus counts: Notes, TapsAndHolds, Jumps, Holds, Mines, Hands, Rolls,
  Lifts, Fakes. Only judgable rows count; unjudgable notes go to Fakes.
  Stream and Chaos are per song length, not per chart-active time, so
  charts with long idle intros or outros read lower than they play
  [INFERRED].
TechCounts (TechCounts.cpp, enum in TechCountsCategory.h) [CODE]
  Crossovers, HalfCrossovers, FullCrossovers, Footswitches, Up/Down
  Footswitches, Sideswitches, Jacks, Brackets, Doublesteps. Totals only, no
  position in time; jack/doublestep/footswitch use elapsed-time cutoffs.
MeasureInfo (MeasureInfo.cpp) [CODE]
  Notes and NPS per 4-beat "measure" (4/4 assumed, per the TODO at the top).
  A row counts as ONE note whatever its width, so jumps and brackets do not
  raise NPS. Hold heads count, tails do not. Fake and warped rows excluded.
  Measures with duration < 0.12 s get NPS 0. peakNps = max over measures.
  Because of the one-note-per-row rule, NPS undercounts "density" for
  jump-heavy and bracket-heavy charts [INFERRED consequence].
StepParity (StepParityGenerator.cpp) [CODE]
  Per row, builds all foot-placement permutations, scores each transition
  (StepParityCost::getActionCost), keeps the cheapest node per distinct
  state (hash key), then takes the cheapest path to the end. Cost is about
  rows x previous-nodes x permutations. Layouts exist only for step types
  where getLayout() returns one; otherwise tech counts stay zero
  (Steps::CalculateTechCounts returns early). [CODE]

------------------------------------------
- Parsed (uncached) load: CalculateStepStats already runs the whole chain,
  including the step-parity search. A rating computed from the quantities
  above adds O(measures) arithmetic to that pass [INFERRED: negligible
  next to the parity search; not measured].

  block (before #STEPFILENAME, which must stay last: comment at
  NotesWriterSSC.cpp ~548-553), a handler in steps_tag_handlers

  a Lua binding, and a bump of FILE_CACHE_VERSION (Song.cpp:69, now 232) so
  old caches regenerate (rule stated in the Steps.h comment ~31-37 for the
  GrooveStats hash version) [CODE for the points; INFERRED that the same
  rule applies to any new tag].

  INFERRED for the consequence].
 
5. LIMITS OF AN "OBJECTIVE" RATING (design, not code) [INFERRED]
----------------------------------------------------------------
- The code gives features, not a target scale. Mapping them to 1-20 needs a
  calibration set with trusted ratings, and every choice (official DDR X
  charts vs an ITG pack) bakes in one community's scale.
- Missing from the cached features: where in time the hard parts occur
  (tech counts are totals), hold-footwork interaction, mine placement
  (counted only), stops/warps/speed gimmicks, reading difficulty, and
  sustained-stamina windows beyond a per-measure NPS array (the array does
  allow a sliding-window stamina feature).
- Doubles/couples/routine need their own calibration; PredictMeter and the
  radar code treat player slots specially (couples are split into halves,
  Steps.cpp ~352-379).
- The step-parity result is itself a heuristic (shortest-path foot guess),
  so tech counts and any cost derived from it inherit its mistakes.

7. PARITY TOTAL COST CHECK (2026-10-09, v1.3.0) [CODE unless tagged]
--------------------------------------------------------------------
a) Where it lives: StepParityGenerator::buildStateGraph (StepParityGenerator
   .cpp ~49-118). Each node's totalCost = previous node's totalCost + the
   transition cost from StepParityCost::getActionCost; per row only the
   cheapest node per distinct state is kept. endNode->totalCost is set to
   the minimum over the last row's nodes (~109-117), so it IS the total of
   the chosen path.
b) Access: endNode is a PRIVATE member of StepParityGenerator (header ~25)
   with no getter. No other file reads totalCost or endNode (grep of src/).
   Steps::CalculateTechCounts (Steps.cpp ~397-403) holds the generator as a
   local and passes only gen.rows on. Exposing it needs a small getter plus
   one more output from TechCounts::CalculateTechCountsFromRows or a new
   Steps member; it would also need a cache tag and a FILE_CACHE_VERSION
   bump (section 4). Alternative with no cache change: recompute the value
   from the rows' stored foot placement is NOT possible (cost needs the full
   state graph).
c) What the cost measures: a sum of penalties used to pick the most
   plausible foot assignment, not a calibrated difficulty. Weights
   (StepParityCost.h): DOUBLESTEP 850, BRACKETTAP 400, FOOTSWITCH 325,
   SLOW_BRACKET 300, SIDESWITCH 130, HOLDSWITCH 55, JACK 30, BRACKETJACK 20,
   DISTANCE 6, FACING 2, MISSED_FOOTSWITCH 500, SPIN 1000, MINE 10000,
   TWISTED_FOOT 100000. Per-transition terms include time-scaled jack and
   footswitch penalties and a distance/elapsedTime movement term.
d) Consequences for use as a rating input [INFERRED]:
   - It grows with chart length (a sum over rows), so it needs normalising
     by rows, notes or active time.
   - Huge weights (TWISTED_FOOT, MINE, SPIN, DOUBLESTEP) mean one forced
     occurrence dominates the total; the metric is lumpy, not smooth.
     Because the search AVOIDS these when it can, a large value flags
     steps that could not be parsed without them (forced doublesteps,
     twists), which is informative, but mine-heavy or odd charts can
     produce outliers unrelated to how hard the chart plays.
   - Penalty weights are tuned for choosing between foot assignments, so
     their relative sizes were not set to match perceived difficulty.
   - Only available where getLayout() returns a layout.
e) Possible defect (observation, not run): calcBigMovementsQuicklyCost
   divides by elapsedTime (StepParityCost.cpp ~448). I found no guard
   against elapsedTime == 0 or an infinity/NaN check anywhere in
   StepParity*.cpp or TechCounts.cpp (grep). Two rows with the same elapsed
   second (e.g. warps or zero-length stops) would give an infinite cost for
   moves; the endNode comparison uses FLT_MAX, so such nodes would lose and
   a chart could end with no valid path ("no valid path found" log).
   CalculateTechCounts ignores analyzeNoteData's return value, so tech
   counts would then be computed from rows with no foot placement set
   [INFERRED, not tested; whether such rows can occur with the layout code
   was not checked].
 
8. Steps:GetTechCounts() LUA SHAPE (2026-10-09, v1.3.0) [CODE]
---------------------------------------------------------------
- Steps.cpp ~1035-1043: optional PlayerNumber argument (nil = PLAYER_1);
  returns a TechCounts userdata object (ts.PushSelf), NOT a table.
- The object has ONE method, GetValue(TechCountsCategory) -> number
  (TechCounts.cpp ~281-291). Same pattern as RadarValues:GetValue. Usage:
    local tc = steps:GetTechCounts(PLAYER_1)
    local jacks = tc:GetValue("TechCountsCategory_Jacks")
  Ten categories: Crossovers, HalfCrossovers, FullCrossovers, Footswitches,
  UpFootswitches, DownFootswitches, Sideswitches, Jacks, Brackets,
  Doublesteps (TechCountsCategory.h). The enum is listed in Lua.xml ~2970;
  I found no class or method entry for TechCounts or Steps:GetTechCounts
  in LuaDocumentation.xml (grep). Steps:CalculateTechCounts() is bound to
  the same function (just returns the cached object, recalculates nothing;
  source TODO says to remove it).
- Values: float. A default-constructed TechCounts holds -1 (MakeUnknown);
  parsed loads Zero() it first, so a step type without a parity layout
  reads 0 for every category (Steps::CalculateTechCounts returns after the
  Zero). Whether any path leaves -1 visible to Lua (e.g. a cache file with
  no #TECHCOUNTS tag) was not checked [UNVERIFIED].
- The object is a reference to the Steps' own member (const_cast), so keep
  values rather than the object across a song reload [INFERRED].
- Per-player slot: all NUM_PLAYERS slots hold copies of player 1's values
  (std::fill_n in CalculateTechCounts), so the argument rarely matters.
- A theme can sum or weight the ten values; GetNpsPerMeasure returns a
  Lua table of numbers (Steps.cpp ~1049-1058, same optional pn argument).

Design consequences [INFERRED, untested]:
 - Partial coverage: treat a chart with a decimal as an exact target and an
   integer-only chart as the interval [L, L+1) (not the bare integer, which
   is the floor and would bias those charts about half a foot low). Fit by
   iterating: fill missing decimals with the model prediction clipped to the
   interval, refit. Missing decimals (the "insufficient data" row) are
   probably concentrated at the top levels; report decimal counts per level.
 - Make the interval SOFT in the loss (Huber-type penalty on distance
   outside the interval) so a few charts the structure puts across a
   boundary do not distort the fit. Complements the planned robust fit and
   outlier report.
 - Possible mis-level flag: a chart whose decimal is at the ceiling or floor
   of its level AND whose model prediction lies beyond that edge. Evidence
   only, not proof.
 - Report two numbers: overall error on all charts, and within-level rank
   correlation on the decimal subset.

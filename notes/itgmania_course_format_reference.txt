1. ANSWER
  The code settles parsing and semantics for essentially every tag and mod string; it cannot settle what a theme
  (Simply Love) does on top, or visual results. Headline findings:
  F1. The three #MODS layouts in Docs/CourseFormat.txt (":" separators, repeated or nested) produce NO attacks and
      NO log message. Only the KEY=VALUE form works (TIME=..:LEN=..:MODS=..), which the shipped example
      "Forced Modifiers (Advanced).crs" and the community guides use. [TESTED 7.1, CODE]. This alone can explain
      "#MODS does nothing" reports from people following the engine doc. Whether it explains the Reddit comment is
      UNVERIFIED (could not read it, 14).
  F2. Per-entry mods (4th field of #SONG) work through the same attack machinery; user test of "failoff" showed they
      apply (course:12.7). Timed #MODS use the same machinery; read-through says they work with the "=" syntax
      [INFERRED, not run; checks M1-M4].
  F3. Full mod vocabulary is enumerable (section 8): 235 literal PlayerOptions tokens, 11 numbered families, speed
      forms, plus 15 SongOptions tokens. Unknown tokens in #MODS: warned at load (log + dialog). In #SONG mods: no load-time warning, but a log line
      "Attempted to load a non-existing mod '<x>' for the Player. Ignoring." when the string is applied [OBSERVED M7].
  F4. Some mods parse but cannot take effect from a course because the engine reads them at Stage or Preferred level
      (life type, visual delay; section 9.3).
  F5. #STYLE is never read; #METER takes Regular/Difficult, not Medium/Hard; several documented statements are wrong
      (section 13).
  F6. Cached courses lose some #SONGSELECT criteria on the second load (GENRE always; DURATION/BPMRANGE when the
      minimum is 0) because the cache writer disagrees with the loader (11.3) [CODE; written-cache side OBSERVED 2026-10-30 (M6); selection effect OBSERVED (M6b)].
  F7. #SONGSELECT came from PR #173 (commits Nov 2023 - Mar 2024, author Michael Votaw; first-release tag not checked);
      the PR's own doc text is in Docs/CourseFormat.txt and is mostly accurate for selection keys (6).

3. FILE-LEVEL SYNTAX (MsdFile::ReadBuf, MsdFile.cpp 31-150)  [CODE]
  - A value is "#NAME:param:param;" . Tag names are matched case-insensitively by the loader.
  - Text outside "#...;" is ignored, so the "--" documentation lines in CourseFormat.txt are harmless.
  - "//" starts a comment to end of line EVERYWHERE, also inside a value (so "//" cannot appear in a title/path).
  - A "#" that is the first non-blank character of a line while a value is open ends that value (missing-";" recovery).
  - ":" and ";" end a parameter; ";" ends the value. Parameters are NOT trimmed (newlines/tabs inside a nested
    layout stay in the text), except the recovery case.
  - Backslash: courses are read with unescape OFF (CourseLoaderCRS.cpp 75, 220). The backslash stays in the string and
    only protects the next character from acting as a control character. So "#COURSE:Foo\: Bar;" gives the title
    "Foo\: Bar" (backslash visible) [CODE read, INFERRED display]. Unescaping is done only inside #SONGSELECT lists (6.3).
  - Consequence: ":" ";" "#" cannot be used in #COURSE/#DESCRIPTION/#SONG names; an unescaped ":" truncates the field.

4. HEADER TAGS (CourseLoaderCRS.cpp LoadFromMsd 79-224)
  tag                  effect / status
  #COURSE:t;           title (field 1 only). WORKS
  #COURSETRANSLIT:t;   WORKS
  #SCRIPTER:t;         WORKS
  #DESCRIPTION:t;      WORKS
  #REPEAT:x;           ENDLESS if the lowercased value CONTAINS "yes" ("yes", "YES", "yesterday"). Any other value: no effect.
  #BANNER:p; #BACKGROUND:p;  paths (relative to the course folder, resolved later). WORKS [path rules not read]
  #LIVES:n;            max(n,0). n>0 makes an ONI (battery) course; ScreenSelectMusic.cpp 1317-1325 then sets battery
                       with n lives (course:10.2 correction). The documented "maximum number of lives" is the real meaning.
  #GAINSECONDS:s;      float, stays in force for EVERY later #SONG until changed (variable never reset, 83/112/140);
                       #SONGSELECT does not use it (152). First entry gain>0 and no #LIVES -> SURVIVAL.
  #METER:n;            custom meter for the Regular (Medium) course difficulty. WORKS
  #METER:Name:n;       Name must be Beginner, Easy, Regular, Difficult, Challenge, Edit (g_CRSDifficultyNames, line 33).
                       "Medium"/"Hard" are INVALID here (logged, skipped) although CourseFormat.txt lists them. TRAP:
                       #SONG's difficulty word "difficult" means the MEDIUM chart slot (Difficulty.cpp 66); here
                       "Difficult" means the Hard course difficulty.
  #MODS: ...;          timed attacks, section 7.
  #SONG: ...;          section 5.      #SONGSELECT: ...;  section 6.
  #STYLE:..;           NOT READ (course:10.3). Reason: the "ignore" branch (lines 156-161) is "!A || !B || !C", true
                       for every name, so later branches (#RADAR cache read, #STYLE, unknown-tag log) never run.
                       Also: typos in tag names are never logged; cached #RADAR lines are not read back. [CODE, same on beta]
  #DISPLAYCOURSE/#COMBO/#COMBOMODE: ignored by design (and so is everything else).
  Course type (Course.cpp 199-209): REPEAT -> ENDLESS; else lives>0 -> ONI; else first entry gain>0 -> SURVIVAL;
  else NONSTOP. SURVIVAL and ONI both use PLAY_MODE_ONI.

5. #SONG:<song>:<chart>:<mods>;  (ParseCourseSong 387-555)  [CODE; most of this is course:10.4]
  field 1: Pack/Song (either slash), bare folder or title, "*", "Pack/*", BEST<n>, WORST<n>, GRADEBEST<n>, GRADEWORST<n>.
           Missing song -> entry skipped, course flagged incomplete (pref HideIncompleteCourses, default false, hides it).
  field 2: difficulty word (old-style synonyms, Difficulty.cpp 55-77) or meter "lo..hi" / "n" (official METER).
           Invalid text -> 3..6 and a log line.
  field 3: comma list. Four keywords are removed and acted on: showcourse, noshowcourse, nodifficult, awardN
           (needs length > 5, so a bare "award" is just an unknown mod; award0 = gain 0 lives). Everything else
           is stored as the entry's mod string (sections 8, 9). Not validated at load; unknown tokens only reach a
           trace line at play time.
  Pending #MODS attach to the entry; GOTCHA: if the #SONG fails to resolve, "continue" skips attacks.clear() so
  the pending timed attacks attach to the NEXT entry that resolves (lines 131-142) [CODE].
  Random entries: "*" and "Pack/*" are secret (title hidden) unless showcourse. Selection RNG is seeded per round:
  GAMESTATE->m_iStageSeed + hash(course title) (Course.cpp 537), so the same course looks the same within a round.
  Same song twice in a row is removed from the candidate list when other candidates exist (602-608).
  Chart choice: ALL charts matching the entry's steps criteria are candidates and one is picked with RandomInt
  (Course.cpp ~633, mappedSongs[RandomInt(..)]) [CODE]. With a meter range such as 1..20 that is any chart of the song, so
  the difficulty can differ between courses and rounds [OBSERVED 2026-10-30: M01 easy+hard, M02 hard+medium for the same
  two songs]. A named difficulty (Easy ...) restricts the candidates. Correction: an earlier reply said the first chart in
  the list is used (SongUtil::GetOneSteps); that is not the path courses take.
  Course difficulty shifting (Course.cpp 640-710): for non-Regular course difficulties the chart slot is shifted
  unless nodifficult (course:3).

6. #SONGSELECT:KEY=value:KEY=value...;  (ParseCourseSongSelect 557-703)  [CODE]
  6.1 Every ":"-piece must split (escape-aware) into exactly two parts at "=", else the WHOLE ENTRY is skipped with a
      log line. So an unescaped "=" in a value (e.g. inside MODS) skips the entry. Unknown key: logged, ignored, the
      entry continues. Keys are case-insensitive.
  6.2 Keys: TITLE GROUP ARTIST GENRE (comma lists) | DIFFICULTY (comma list) | METER=lo-hi | BPMRANGE=lo-hi |
      DURATION=lo-hi | SORT=name,index | GAINLIVES=n | GAINSECONDS=n | MODS=list. A key given twice appends.
  6.3 Escapes: TITLE/GROUP/ARTIST/GENRE items are split on unescaped "," and passed through SmUnescape, so \, \= \: \;
      \# \\ work there (PR #173 added this). DIFFICULTY, SORT, MODS values are not unescaped.
  6.4 Matching (SongUtil.cpp SongCriteria::Matches 50-139): GROUP exact and CASE-SENSITIVE (unlike #SONG's Pack/ part);
      TITLE exact against folder name, #TITLE or #TITLETRANSLIT (not subtitle); ARTIST against #ARTIST or
      #ARTISTTRANSLIT; GENRE exact on #GENRE; BPMRANGE uses displayed BPMs and needs min >= lo AND max <= hi;
      DURATION compares the song's music length; locked/disabled and tutorial songs are excluded.
  6.5 Numbers: ParseRangedValue splits on "-", requires first <= last, accepts decimals but METER is cast to int
      (8.9-12 -> 8-12). A single value "8" means 8-8. Docs say "whole numbers only" for BPM/DURATION; the code
      accepts decimals. GAINSECONDS is read with StringToInt (fraction dropped); GAINLIVES int.
  6.6 DIFFICULTY: invalid names are logged and skipped; if all are invalid the entry has no difficulty filter.
  6.7 MODS=: keywords showcourse/noshowcourse/nodifficult only (NO award; use GAINLIVES). Rest = mod string as in #SONG.
  6.8 If no song matches, the entry is skipped (documented). #MODS before it attach to it.

7. #MODS (timed attacks)  (ParseCourseMods 340-385)  [CODE + TESTED]
  7.1 Syntax that works. Each ":"-piece is split at "=": TIME=s, LEN=s, END=s, MODS=list. A piece WITHOUT "=" is
      skipped silently (no log). Results of the synthetic run (real ReadBuf and ParseCourseMods text):
        "=" form, LEN or END ........................ attack(s) created
        several groups in one #MODS ................. all created
        docs format 1 "#MODS:TIME:0.500:LEN:0.500:MODS:2x;" ........ 0 attacks, no log
        docs format 2 (nested, ":" separators) ...................... 0 attacks, no log
        docs format 3 (nested with END, ":") ........................ 0 attacks, no log
        CourseWriterCRS cache format (nested, "=", ":" between groups) ... 2 attacks (cache round trip OK)
  7.2 Group rules: a "MODS=" piece completes a group using the TIME/LEN/END seen so far in the same #MODS.
      TIME and LEN PERSIST into the next group (a second group may omit LEN and inherits it); END is cleared after
      use. Key order matters: MODS before TIME/LEN gives start=-10000 (unset) and len 0 -> never active.
      END converts to LEN = END - TIME. LEN <= 0: logged ("nonpositive length") and set to 0 (attack never active).
      Negative TIME clamps to 0. Keys are trimmed and case-insensitive; values are not trimmed (mod string keeps
      trailing spaces; harmless). A mod string containing "=" is cut at the "=" ("foo=bar" -> "foo").
  7.3 A #MODS applies to the NEXT #SONG/#SONGSELECT only; one with no following entry is dropped; one after the entry it
      was meant for applies to the following entry (TESTED).
  7.4 Validation: each mod string goes through CourseUtil::WarnOnInvalidMods (CourseUtil.cpp 374): tokens accepted by
      neither PlayerOptions nor SongOptions are logged ("Error processing ..."). Warning only; the attack is kept.
      Not applied to #SONG mods.
      [OBSERVED 2026-10-30, M7, user's Windows run] Load of an uncached course: log "Error processing 'x' in 'x'" (the
      message prints the token, then the whole comma list it came from) AND a modal dialog [INVALID_PLAYER_OPTION_WARNING],
      shown once at load. #SONG mod 'cref_bad_song_token': no load-time message (as predicted). BUT PlayerOptions::FromString
      (PlayerOptions.cpp 753-766) logs "Attempted to load a non-existing mod '%s' for the Player. Ignoring." at Trace level
      for every unknown token whenever a mod string is applied. Observed for BOTH tokens: 5 pairs in one burst when the
      course list was built (about 5 = one per course difficulty [INFERRED]) and again 1 pair when the course was started.
      So "silently ignored" was wrong; correct: no dialog and no load-time warning for #SONG tokens, but logged when applied.
      The same run logged "Launch attack 'cref_bad_mods_token' against P1 at 1.000000" at gameplay start [OBSERVED]:
      a #MODS TIME=1 entry in "=" form does create and launch an attack.
  7.5 Time base [CODE, base INFERRED]: TrailEntry attacks go to ScreenGameplay m_asModifiersQueue[songIndex]. SetupSong
      (1223-1232) launches them for that song; GameState::ResetMusicStatistics runs at the start of LoadNextSong
      (1251) and resets the position to 0 (SongPosition.h 42). PlayerState::Update enables an attack while
      start < musicSeconds < start+len (PlayerState.cpp 74-77). So TIME is seconds of music time from the start of
      THAT entry's song, not cumulative over the course. (An old FFR guide says timing "must continue across
      songs"; that does not match this code.)
  7.6 TIME=0 is special: SetupSong turns start==0 into "start now" (1226) and LaunchAttack stores the current music
      seconds (0 after the reset) as the start, so TIME=0 behaves as 0. [CODE]
  7.7 Option mods vs note-data mods [CODE read, behaviour INFERRED]:
      - Option mods (speed, boost, reverse, drunk, hidden...) turn on/off with the attack window through
        RebuildPlayerOptionsFromActiveAttacks (Song level = Stage + attacks that are on).
      - Turn/transform mods (mirror, shuffle, little, noholds...) are NOT toggled in time. Each attack's string is queued
        in m_ModsToApply and applied once to the NOTE DATA over a beat range (Player::ApplyWaitingTransforms
        1722-1748). Timed attacks (start > 0): range from the song's timing (Attack::GetAttackBeats). "no mirror" at the end
        does not undo anything.
      - [SUPERSEDED BY THE CORRECTION BELOW] For a TIME=0 attack the sentinel start is used (GetRealtimeAttackBeats, Attack.cpp 29-57): start beat is pushed
        to min(songBeat+8, lastDrawnBeat) = about beat -99 at song setup, and the end is start-second + LEN. Because the
        start second is that of beat -99 (negative, about -50 s at 120 BPM), the covered range may be SHORTER than
        LEN (e.g. LEN=60 might cover only part of the song) [INFERRED, check M3].
      CORRECTION 2026-10-30 after M3 [OBSERVED log]: the "about beat -99" reading above is WRONG. The user's log for
      #MODS:TIME=0:LEN=20:MODS=mirror on song 2 says: "Launch attack 'mirror' against P1 at -10000.000000" (the sentinel,
      as predicted) and then "Applying transform 'mirror' from 6.000000 to 49.000000". So the range started at beat 6
      (start = trunc(min(songBeat+8, lastDrawnBeat))+1; the transform is applied from the first Player::Update after the
      song starts, when the song beat is still slightly negative and the note field has already drawn) and ended at beat 49,
      i.e. about the full LEN (43 beats = 20 s only if the song is about 129 BPM; BPM not reported). Hypothesis that the
      range lay before the song is disproved. Real effect of TIME=0 on turn/transform mods [CODE + OBSERVED]: they begin
      about 8 beats (roughly 3-4 s) after the song start, not at 0, and notes before that stay unmodified; then LEN seconds.
      Whether the mirror was visible on screen is unknown: the user saw no change, but could not compare with an unmodified
      chart and the chart was a random pick. The log proves it was applied to the note data, not that mirror changed any
      notes in that range. M3b/M3c (mod "big") test visibility.
      Option mods (reverse) are unaffected: they work by attack window, as M1 showed.
  7.8 SetupSong also applies every attack's SongOptions part immediately (1231); the later rebuild generally replaces
      it. Effect for music-rate or other song-level mods inside TIMED attacks is unclear [UNVERIFIED].
  7.9 Theme sounds "course attack launch"/"course attack ending" are loaded by Player (Player.cpp 483-486).

  8.3 Quirks [CODE]:
      a) Substring gates: names containing wave, expand, dwiwave, drunk, shrink, pulse, dizzy, confusion, bounce, tiny,
         tornado, tipsy, bumpy, beat, digital, zigzag, sawtooth, square, parabola, attenuate, stealth, reverse, dark,
         move, lights, modtimer, drawsize enter a branch that returns TRUE even when no exact token matched. A typo
         such as "wavy" ... "wavefoo" is accepted silently, so WarnOnInvalidMods cannot catch it. A noteskin whose
         name contains one of these substrings could never be selected by mod string (none of the shipped dance and
         pump skins do).
      b) A noteskin name with a space matches only at the end of the chain: the skin is set but the function returns
         false, so WarnOnInvalidMods logs a false warning.
      c) An empty/whitespace-only mod (e.g. "flip, ,mirror" or a trailing ", ") makes asParts empty and
         asParts.back() (line 818) is undefined behaviour. #SONG mods are safe (empties removed at 546-552), but #MODS
         strings reach WarnOnInvalidMods unfiltered [CODE, TESTED that the string arrives intact]. Possible crash
         [INFERRED; not run].
      d) Invalid mods in #SONG are only trace-logged at play time.
  8.4 SongOptions tokens (SongOptions.cpp 151-): Nxmusic (music rate, e.g. 1.5xmusic), clap, metronome, autosync
      autosyncsong autosyncmachine autosynctempo, "no effect", effectspeed effectpitch, staticbg randombg, savescore
      savereplay, haste. "no X" turns off; a leading percent is ignored ("50% haste" = on). A mod string is fed to both
      PlayerOptions and SongOptions; each ignores what it does not know. Song-level SongOptions are only assigned for
      the master player (PlayerState.cpp 179).

9. PIPELINE AND LEVELS
  9.1 Stages [CODE]: #SONG field 3 -> CourseEntry.sModifiers -> Trail entry .Modifiers -> TrailEntry::GetAttackArray
      (Trail.cpp 22-28) adds Attack::FromGlobalCourseModifier (start 0, length 10000, global) + the entry's timed
      attacks -> ScreenGameplay queue -> SetupSong: LaunchAttack -> RebuildPlayerOptionsFromActiveAttacks (Song level =
      Stage + attacks on) -> Current approaches Song every frame; turn/transform strings also go to m_ModsToApply.
      Because course mods live at Song level, they do not alter the player's saved options or later screens.
  9.2 Classification
      WORKS (acted on): #MODS "=" form; #SONG/#SONGSELECT keywords; PlayerOptions and SongOptions tokens at levels the
        engine reads (9.3); turn/transform mods (entry-wide; timed range per 7.7).
      PARSED, CANNOT TAKE EFFECT: options read at Stage/Preferred level (9.3).
      PARSED, IGNORED: unknown mod tokens; #DISPLAYCOURSE/#COMBO/#COMBOMODE; #STYLE (never reached); cached #RADAR
        (never read back); "award" without a number.
      NOT PARSED: #MODS ":" layouts of CourseFormat.txt (silently dropped); any other unknown tag.
      UNVERIFIED: forced noteskins (an engine hack launches noteskin attacks before Player::Load, ScreenGameplay.cpp
        1160-1177, and NoteField reads Current, but the shipped example and the wiki say it does not work; and the
        reset at 1239 touches Current); survival-course option override (theme metric SurvivalModOverride, default
        true: resets to clearall + default noteskin + DefaultModifiers before entry mods, 1024-1031).
  9.3 Level the engine reads (grep of consumers, v1.3.0):
      Current (course mod effective): FailType, passmark, muteonerror, disabled windows, playerautoplay, cosecant,
        zbuffer, modtimer, all ArrowEffects options, NoteField noteskin.
      Song: DrainType (LifeMeterBar 159-271; the constructor reads Stage at 93), battery max lives (LifeMeterBattery
        95-258; initial lives read from Stage at 32).
      Stage: LifeType (bar/battery/lifetime: Player 713, 2125; ScreenGameplay 683-731) -> a course mod "battery"/"bar"
        will not change the life meter type [INFERRED; check M8].
      Preferred: visualdelay (GameState.cpp 1262) -> no effect from a course.
      Not checked: hide-lights options.

10. LIVES, AWARD, GAINSECONDS
  - #LIVES n>0: ONI/battery with n lives at selection (course:10.2).
  - awardN / GAINLIVES: LifeMeterBattery::OnSongEnded adds the entry's gain when > -1, else calls the theme's
    CourseSongRewardLives Lua callback (LifeMeterBattery.cpp 95-110); default -1.
  - #GAINSECONDS: LifeMeterTime adds the entry's seconds at each song start (LifeMeterTime.cpp 107-137); only
    meaningful for SURVIVAL.
  - Priority when several are present: REPEAT > LIVES > GAINSECONDS (Course.cpp 199-209). The RhythmLunatic wiki
    states the opposite order; the code wins. #LIVES with #GAINSECONDS: ONI wins and gain seconds are unused.

11. LOADING, CACHE, WRITER
  11.1 LoadFromCRSFile (226-296): uses Cache/Courses/<file> when it exists and (FastLoad true [default] or the .crs hash
       matches). The cache is written after a non-cached load once radar values exist (course:5.5).

1.2 How the list is used [CODE: RageSoundDriver.cpp Create;
    RageSoundManager.cpp pref "SoundDrivers", default ""]
  - Empty pref = platform default list.
  - A non-empty SoundDrivers value is split on ",". Each entry is checked
    against the platform's DEFAULT list (exact std::find, so CASE-SENSITIVE
    here, unlike input drivers); entries not in it are removed with a
    log warning and a user-facing warning (WarnUserAboutBadSoundDriverEntry).
    If nothing is left, the default list is used. [CODE]
  - So to keep the old behaviour on beta, set SoundDrivers=DirectSound-sw
    (or a list starting with it) in Preferences.ini. [INFERRED from the
    above; not tested]
  - If a driver's Init() returns an error the log says "Couldn't load
    driver X: <error>" and the next one is tried; the chosen one logs
    "Sound driver: X". [CODE] So a WASAPI failure falls back silently
    (to DirectSound-sw) apart from Log.txt.
 
1.3 What the WASAPI driver does [CODE: RageSoundDriver_WASAPI.cpp]
  - SHARED mode only (AUDCLNT_SHAREMODE_SHARED), event-driven
    (EVENTCALLBACK). There is no exclusive mode and no preference for it.
  - Device: the system DEFAULT render endpoint (GetDefaultAudioEndpoint,
    eRender, eConsole). No device-selection preference.
  - Format: uses the endpoint's shared-mode MIX format as-is. Accepted only
    if WAVE_FORMAT_EXTENSIBLE with IEEE float, or 16-bit PCM. Anything else
    (e.g. 24-bit or 32-bit integer mix format) makes Init fail with
    "Unsupported format ..." and the engine falls to the next driver.
    Sample rate = the mix format's rate. [CODE]
  - Buffer: hnsRequestedDuration = 0 (system default) unless the existing
    preference SoundWriteAhead (frames, default 0) is non-zero, in which
    case frames are converted to 100 ns units at the device rate. [CODE]
    Whether the system honours the request in shared mode was not
    checked. [UNVERIFIED]
  - Threads: "WASAPI Mixer Thread" at TIME_CRITICAL priority (falls back to
    ABOVE_NORMAL), plus the shared decode thread at ABOVE_NORMAL. [CODE]
  - Mixer loop: wait on the audio event (2 s timeout; on timeout it logs
    "WASAPI: Timeout waiting for audio event" and does Stop()+Start()),
    then fills all free buffer space (buffer size minus padding). [CODE]
  - Position: IAudioClock::GetPosition scaled to frames; on failure returns
    0. Latency: IAudioClient::GetStreamLatency (0 on failure). [CODE]
  - Decode buffer = 1.5 x the WASAPI buffer size. [CODE]
  - Log line on success: "WASAPI: Shared mode, N channels, R Hz, Float|
    Int16, buffer size B frames". [CODE] Useful to see what you got.

2.1 Enabling it [CODE: LightsManager.cpp ~35, ~116; LightsDriver.cpp
    Create; LightsDriver.h REGISTER_LIGHTS_DRIVER_CLASS]
  - Preference LightsDriver (Preferences.ini), comma-separated list.
    Empty = DEFAULT_LIGHTS_DRIVER = "SystemMessage,Export". A non-empty
    value REPLACES that default (so "brokeio" alone drops SystemMessage and
    Export). Registered name is "brokeio"; matching is case-insensitive
    (istring map, same mechanism as input drivers). Unknown names are
    skipped with a Trace log. [CODE; the replace-not-add reading is
    INFERRED from the empty-check, not tested]
  - Compiled on all platforms: the file is in the unconditional part of
    CMakeData-arch.cmake. [CODE] The header comment only gives Linux
    udev examples; on Windows/macOS whether hidapi can open the board
    without extra setup was not checked. [UNVERIFIED]
  - Hardware: USB HID vendor 0x1D50, product 0x6181; the header calls it
    "the brokeio board (in gamepad mode)" using hidapi. Nothing else about
    the hardware is known from the code. [CODE]
  - Linux: needs user read/write on the device, e.g. udev rule on
    ATTRS{idVendor}=="1D50", ATTRS{idProduct}=="6181" (usb subsystem) or
    KERNEL=="hidraw*"; the example uses OWNER/GROUP "dance", MODE 0660.
    Those names are example values in the comment. [CODE]
 
2.2 What it sends [CODE: brokeio.h enum, brokeio.cpp Set]
  One HID output report of 17 bytes: byte 0 = report id 0x00, then 16
  light bytes, each 0xFF (on) or 0x00 (off), so no dimming:
    idx 1-5   P1 pad: UL, UR, CN, LL, LR
    idx 6-10  P2 pad: UL, UR, CN, LL, LR
    idx 11    NEON       = LIGHT_BASS_LEFT OR LIGHT_BASS_RIGHT
    idx 12-15 MARQUEE UL, UR, LL, LR  <- cabinet lights UP_LEFT, UP_RIGHT,
              LR_LEFT, LR_RIGHT (in that order: UL=UP_LEFT, UR=UP_RIGHT,
              LL=LR_LEFT, LR=LR_RIGHT)
    idx 16    COIN_PULSE = m_bCoinCounter
  The static_assert checks the enum length equals 17.
  Game button lights depend on the CURRENT game's input scheme name,
  compared case-insensitively, read on every Set() call:
    "dance": P1_UL=Up, P1_UR=Down, P1_CN=Left, P1_LL=Right (same for P2);
             the LR byte is not written.
    "pump":  UL=UpLeft, UR=UpRight, CN=Center, LL=DownLeft, LR=DownRight.
    any other game: pad bytes are not written at all.
  Menu/Start button lights are not sent. [CODE]
 
2.3 Write behaviour [CODE]
  - Set() returns early until dev.FoundOnce() is true (device seen at
    least once).
  - The report is written only when the 17 bytes differ from the previous
    ones (memcmp), then prev is updated.
  - Uses HidDevice (autoReconnection default true). HidDevice::Write
    returns Success / NotConnected / OperationFailed; on a failed hid_write
    it logs "HidDevice ... write failed" and closes the handle.
 
2.4 Observations (not confirmed defects)
  a) Odd dance mapping [CODE for the mapping; UNVERIFIED whether intended]:
     dance Up/Down/Left/Right go to the slots named UL/UR/CN/LL, i.e. the
     pump-style five-panel names. This may match how the board wires four
     dance lights, or may not. LightsDriver_snek maps dance buttons
     Up/Down/Left/Right by name, but that says nothing about this board.
     Check on hardware which physical light each pad byte drives.
  b) Stale bytes [CODE for the buffer being persistent; INFERRED for the
     effect]: outputBuffer is a member and only some bytes are written per
     game. Switching pump -> dance leaves the LR byte at its last pump value
     (dance never clears it). Running a game that is neither dance nor pump
     leaves pad bytes at whatever they last were. Not tested.
  c) Failed write not retried [CODE for ignoring the return value and
     copying prev unconditionally; INFERRED for effect]: after a failed or
     disconnected write, prev already equals the new state, so lights are
     not resent until some light changes. After a reconnect the board could
     show stale lights until then. Not tested.
  d) prevOutputBuffer is not initialised [CODE: the constructor
     initialises only outputBuffer{0}]. The first memcmp compares against
     indeterminate memory; the practical effect is at most one skipped or
     extra first write (if garbage happened to equal the first state).
     Harmless in practice [INFERRED].
  e) Bass lights map to a single NEON byte (either bass side lights it).
  f) Set() is not guarded by Threaded-input or any lock; LightsManager
     calls it from its update; nothing threaded seen. [INFERRED, not
     deeply checked]

4. WEBSOCKET PER-MESSAGE DEFLATE (Lua NETWORK:WebSocket "enableDeflate")
=======================================================================
Basis: itgmania beta head 28e58a78c7; commit 2714ea8ada (2026-07-18,
  "Brandon W", "Add deflate arguments for network handler, to allow for
  compressed websocket connections."); IXWebSocket library source at the

  64fae7676b = tag v12.0.1, bumped by dependabot commit 181461057a,
  2026-07-01). Not built, not run, no server to test against.
  Not in v1.3.0 [CODE: git merge-base]. Files: src/NetworkManager.cpp/.h
  only (+19 lines).
Docs: grep of Docs/ and Themes/ for "deflate" finds nothing about this
  option. The Lua doc entry for NETWORK:WebSocket (LuaDocumentation.xml
  ~3762, "since ITGmania 0.5.1") lists url, headers, handshakeTimeout,
  pingInterval, automaticReconnect, onMessage; it does NOT list
  enableDeflate. [CODE, grep]
 
4.1 What the commit does [CODE]
  - New Lua table field to NETWORK:WebSocket{}: enableDeflate (boolean).
    Absent or nil = TRUE. A non-boolean value raises the Lua error
    "enableDeflate must be a boolean".
  - NetworkManager::WebSocket calls webSocket.enablePerMessageDeflate() if
    true, else disablePerMessageDeflate(), before connecting.
  - So on beta every WebSocket opened without the field now ASKS the
    server for the "permessage-deflate" extension. enableDeflate=false
    restores the old behaviour.
 
4.2 What the default was before [CODE: IXWebSocket at 2efe037c9c]
  The library's own default is OFF: WebSocketPerMessageDeflateOptions
  defaults to enabled=false, and WebSocket() does not set it. NetworkManager
  at v1.3.0 never touched the setting (grep: no deflate calls). So at
  v1.3.0 no compression was ever offered. The commit message says
  "to allow for compressed websocket connections"; in effect it also
  changes the default from off to on. [CODE for both states; the
  "default changed" reading is my summary]
  zlib support is compiled in for both versions: ixwebsocket is built
  with IXWEBSOCKET_USE_ZLIB (CMakeProject-ixwebsocket.cmake line 114 at
  v1.3.0 and on beta). Without that define the library would ignore the
  request. [CODE]
 
4.3 How negotiation works [CODE: IXWebSocketHandshake.cpp,
    IXWebSocketPerMessageDeflateOptions.cpp, IXWebSocketTransport.cpp,
    library v12.0.1]
  - Client handshake adds the header
      Sec-WebSocket-Extensions: permessage-deflate; server_max_window_bits=15;
      client_max_window_bits=15
    (no *_no_context_takeover parameters; both window sizes 15, the max).
    enablePerMessageDeflate() uses the defaults of the options object.
  - If the server's reply has no matching extension, deflate is turned off
    for that connection and the socket works as before.
  - If the server accepts it but the zlib engine fails to initialise, the
    handshake is reported as failed ("Failed to initialize per message
    deflate engine"), so the connection fails instead of falling back.
    [CODE; I know of no reason init would fail; not tested]
  - When active, sent text/binary messages are compressed and received
    frames with RSV1 are decompressed transparently. The Lua onMessage
    callback gets the plain data; nothing in the Lua message table says
    whether compression was used. [CODE for the transport flags; the Lua
    side was not re-read for an indicator: INFERRED]
  - The server must support it; a server that does not just ignores the
    header. A strict server that rejects unknown extensions could refuse
    the handshake [INFERRED; not tested; no server known].
 
4.4 Who is affected

  b) Silent default change [INFERRED to matter only for servers that

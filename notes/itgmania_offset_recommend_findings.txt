1. THE IDEA (user, 2026-10-14)
 F6 Machine autosync gets the audio calibration "close" but leaves a consistent residual.
 Proposal: look at timing offsets over a whole multi-song session and recommend a Global
 Offset change. Rationale: individual songs are synced early or late (undocumented which,
 and in which direction); averaging many songs should wash that out.
 Assumption stated for design: the library holds packs flagged NULL and packs flagged ITG
 (the 9 ms pack offset), handled by Pack.ini.

2. ANSWER
 Feasible in a theme's Lua; no C++ change needed. [CODE] for every data path below.
 Simply Love already records every tap offset per stage (section 11), so the theme side
 is mostly aggregation. Session boundaries are known (section 12). Engine autosync reset
 behaviour is known (section 13). The relevant code is unchanged on engine beta and on
 upstream Simply Love (section 14). Not yet built.

7. PACK SyncOffset (NULL vs ITG) AND WHAT IT MEANS FOR THE AVERAGE
 [CODE] Group.cpp:62-71: default m_fSyncOffset = 0 if pref DefaultSyncOffset is NULL, else
        -0.009. Group.cpp:118-134: Pack.ini [Group] SyncOffset=NULL -> 0; =ITG -> -0.009;
        other values log a warning. Code comments: ITG means "remove the 9ms ITG bias";
        NULL is "what we shift everything to".
 [CODE] Song.cpp:433-435, 488-491, 514-517, 679-681: the group offset (fallback 0 / -0.009
        by DefaultSyncOffset) is stored in m_fBeat0GroupOffsetInSeconds of the song and every
        Steps timing. TimingData.cpp:799 and :875 add it to the beat-0 offset.
 [CODE] Group Lua binding exposes GetSyncOffset (Group.cpp:183). Simply Love already calls
        SONGMAN:GetGroup(song):GetSyncOffset() (Graphics/MusicWheelItem Course NormalPart.lua:27).
 CONCLUSION (corrects an earlier loose statement):
 [INFERRED] The pack offset is a NORMALIZING shift applied at load, before judgment. If a
        pack's flag matches how it was actually synced, a NULL-pack song and an ITG-pack song
        give the same mean offset for the same player and hardware: no built-in 9 ms spread.
        The reason the flag exists is so one Global Offset works across both kinds of pack.
 [INFERRED] A residual ~9 ms spread appears only where a flag is wrong or missing: a pack
        with no Pack.ini falls back to DefaultSyncOffset (Group.cpp:70-71), correct only if
        those packs really are synced that way.
 [UNVERIFIED] Whether flag-corrected data is flat in practice. The 9 ms is a convention;
        individual packs and songs still vary (the scatter the feature wants to average).
 DESIGN RULES
  a. Do not subtract the group offset from collected offsets (that undoes the normalization).
  b. Log the group's SyncOffset (GetSyncOffset) with every song record.
  c. Report the recommendation overall AND per pack/flag. A NULL-vs-ITG gap near 9 ms in
     the user's own data would indicate a mis-flagged pack or a wrong DefaultSyncOffset.

8. DESIGN IMPLICATIONS
 - Use the same window as autosync (W1-W3) so outliers do not drag the mean; a stricter or
   trimmed window is a design choice. Simply Love's stored data includes W4/W5 and misses
   (section 11), so the filter must be applied by the new code.
 - Average per-song means (equal weight per song), then median or trimmed mean across songs.
 - Record per song: chart identity (hash/path), pack, group SyncOffset, n, mean, stddev,
   music rate. Sorted residuals would start documenting early/late songs.
 - Variance alone has no direction; the signed mean is required.
 - Check correlation of residuals with BPM / notes per second (hardware latency vs reaction
   bias) before trusting a single number.
 - Music rate: the engine divides by rate (section 3), so offsets are already in chart time.
 - Session scope (section 12): the data lives only in memory and is wiped at the title menu,
   so a recommendation that should span several visits needs its own on-disk log.
 - F6 interaction (section 13): if Machine autosync is used during the session, the global
   offset can change between songs, so offsets from later songs are measured against a
   different offset than earlier ones. The recommender must account for that (13.5).

13. ENGINE: PER-SONG AUTOSYNC RESET (S3, read 2026-10-15, v1.3.0)
 13.1 The mode (m_AutosyncType) resets to the preferred value at every stage start.
  [CODE] ModsGroup.h:12-17 levels, in order: Preferred, Stage, Song, Current ("Current
         approaches Song"). ModsGroup::Assign(level, v) copies v into every level from
         `level` up to but not including Current, and also into Current unless level is Song
         (ModsGroup.h:79-86).
  [CODE] ScreenDebugOverlay.cpp ~778 (F6) assigns m_AutosyncType at ModsLevel_Song only. So
         F6 changes Song (and, via ModsGroup::Update -> Approach, Current; SongOptions::Approach
         copies m_AutosyncType with DO_COPY, SongOptions.cpp:42) but leaves Stage and
         Preferred untouched.
  [CODE] GameState::BeginStage (GameState.cpp:723; called from ScreenGameplay.cpp:506,
         "called once per stage") does
         m_SongOptions.Assign(ModsLevel_Stage, m_SongOptions.GetPreferred()) (GameState.cpp:743-744)
         unless ARE_STAGE_SONG_MODS_FORCED. That copies Preferred into Stage, Song and Current,
         overwriting the F6 setting.
  [INFERRED] Result: F6 autosync set during song N lasts to the end of song N and is Off again
         on song N+1 (unless the Preferred value is itself autosync, below). F6 must be pressed
         again each song.
  [CODE] Exception 1: SongOptions::FromString accepts "autosync", "autosyncsong",
         "autosyncmachine", "autosynctempo" (SongOptions.cpp:181-185). If any of these is in the
         player's default/preferred modifiers, every song would start with that mode.
         [UNVERIFIED] whether any theme or the user's setup puts it there.
  [CODE] Exception 2: ScreenGameplaySyncMachine (the sync-machine screen) assigns
         AutosyncType_Machine at ModsLevel_Stage (ScreenGameplaySyncMachine.cpp:65-67).
  [CODE] Exception 3: PlayerState::RebuildPlayerOptionsFromActiveAttacks rebuilds Song from
         Stage (PlayerState.cpp:167-180) when attacks start/end (callers PlayerState.cpp:95,
         139, 151; ScreenGameplay.cpp:1030, 3105). [INFERRED] Songs with attacks/mods queues
         could clear an F6 setting made at Song level mid-song; not verified.
 13.2 The sample buffer resets every stage.
  [CODE] BeginStage calls AdjustSync::ResetOriginalSyncData() (GameState.cpp:734), which
         records s_fGlobalOffsetSecondsOriginal = current GlobalOffsetSeconds and calls
         ResetAutosync() (AdjustSync.cpp:82-87): s_iAutosyncOffsetSample = 0 and the tempo
         data is cleared. GameState.cpp:342 (game reset) calls it too.
  [CODE] After a completed batch AutosyncOffset() also zeroes s_iAutosyncOffsetSample
         (AdjustSync.cpp:231), whether or not the correction was applied.
 13.3 Consequences of 13.2:
  [INFERRED] A partial batch (fewer than 24 qualifying W1-W3 taps) at the end of a song is
         discarded. A song with fewer than 24 qualifying taps contributes nothing.
  [INFERRED] There is no carry-over of samples between songs; batches never span songs.
 13.4 Persistence of an applied correction:
  [CODE] Machine autosync sets GlobalOffsetSeconds in memory immediately when a batch passes
         (AdjustSync.cpp, Set(GlobalOffsetSeconds + mean)). Writing it to disk happens only if
         the end-of-song sync prompt is accepted (SaveSyncChanges), else RevertSyncChanges
         restores s_fGlobalOffsetSecondsOriginal (the value recorded at stage start).
 13.5 Design consequences:
  a. If the player uses F6 during a session, the in-memory Global Offset can change within a
     song (after each passing 24-tap batch) and between songs. Tap offsets recorded after a
     change are relative to the new offset, those before to the old one.
  b. For a clean recommendation, either (i) collect with F6 off, or (ii) record
     GlobalOffsetSeconds at each stage start (and, if wanted, at stage end) and convert each
     song's mean to a common reference: the recommendation for a song measured under offset G_s
     is G_s - mean_s; pool those recommended values, not raw means. [INFERRED] from the
     sign rule in section 4. Within-song changes make (ii) approximate for songs where
     autosync fired.
  c. If the user rejects the end-of-song sync prompt, the offset reverts to its stage-start
     value, so the next song starts again from the old offset.

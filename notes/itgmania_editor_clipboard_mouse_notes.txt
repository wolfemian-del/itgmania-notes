   - Beta: m_UndoStack and m_RedoStack, each entry = full NoteData copy
     plus a text description; MAX_UNDO_STATES = 50 (oldest dropped).
     SaveUndo(description) pushes and CLEARS the redo stack.
     Undo/Redo show system messages "Undo - <description>" / "Redo -
     <description>", or "Can't undo/redo - no ... data".
   - Stacks are cleared in ScreenEdit::Init (ClearUndo), so history does

   - The undo state holds NOTE DATA ONLY. Timing changes (BPM, offset,

     10 call sites (11 lines incl. the definition; the earlier note said

   - Memory [INFERRED, arithmetic only]: up to 50 full copies of the
     chart's note data per open editor, plus 50 in the redo stack.
     Note data for typical charts is small; a very dense chart is a
     larger multiple. Not measured.
   - CheckNumberOfNotesAndUndo (notes past the end): now compares against
     the top of the undo stack and drops the reverted state from the redo

4. Clipboard [CODE: ScreenEdit.cpp ~7440-7560]
   - Cut/Copy need a selected area (begin and end markers); otherwise the
     message "Nothing selected - use Select an area first." and an
     invalid sound. Paste on an empty clipboard: "Clipboard is empty -
     nothing to paste."
   - The clipboard (m_Clipboard, clipboardFullTiming, s_bClipboardHasTiming)
     is now STATIC, so it persists between charts and between editor
     sessions within one game run; copying from one chart and pasting into
     another is the stated purpose (commit message). Not saved to disk.
   - Init calls m_Clipboard.SetNumTracks(current chart's track count).
     NoteData::SetNumTracks resizes the track vector: it does not clear
     the notes, but a clipboard made from more tracks than the new chart
     has would be truncated, and one from fewer gets empty extra tracks.
     [CODE for SetNumTracks; INFERRED for the effect on pasting across
     steps types; not tested]
   - Timing variant (Shift): cut/copy copies the timing segments in the
     range (TimingData::CopyRange, all segment types) from the

     cut also clears that range (ClearRange) and marks dirty. Paste
     copies clipboardFullTiming into the appropriate timing at the current
     row. Paste without Shift never pastes timing; Shift-paste pastes
     timing only if the clipboard was made with Shift.

     The menu entry "Paste timing from clipboard" already existed.
   - Undo does not restore timing (see 3). [INFERRED from 3]

5. Mouse wheel [CODE: ScreenEdit::Input ~2953-3025, Update ~2418,
   ~3270-3290]
   Only in the editing state and only when the wheel event is not mapped
   to an edit button.
   - Wheel: scrolls one "line" (same action as the keyboard line scroll).
   - Shift+wheel: one page (4 beats).
   - Ctrl+wheel: steps the notefield scroll speed through the presets
     (same as Ctrl+Up/Down); this is what gives the "zoom" effect in the
     editor (commit message). Plays the marker sound when the value
     changes.
   - Acceleration: consecutive wheel events within 0.5 s (hard-coded
     SCROLL_ACCELERATION_RESET_TIME) ramp a multiplier:
     1 + (n-1) x ScrollWheelAccelerationRate, capped at 8 (hard-coded
     MAX_SCROLL_ACCELERATION_MULTIPLIER). Line scrolls move
     beats x multiplier; Ctrl+wheel jumps round(multiplier) presets per
     tick.
   - The display "trailing beat" catches up faster when the multiplier
     is above half the cap (4).
   Theme metrics [ScreenEdit], defaults in _fallback/metrics.ini
   ~4160-4165 [CODE]:
     ScrollWheelAccelerationRate=0.1
     ScrollSpeedApproachRate=10   how fast the displayed scroll speed
                                  catches up to a new preset (applied to
                                  the edit field's player options)
     ScrollSpeedPresets="1.0,1.5,2.0,3.0,4.0,6.0,8.0,12.0"
   Presets are parsed at Init; an empty or unparseable list falls back to
   1,1.5,2,3,4,6,8 (note: no 12). InvertScrollSpeedButtons (existing
   metric) also inverts the direction of Ctrl+wheel. [CODE]
   Observations (not confirmed defects):
   a) Stale multiplier [CODE for the assignments; INFERRED for the
      effect]: m_fScrollAccelerationMultiplier is reset only inside the
      wheel handler, on the next wheel event after more than 0.5 s. The
      line-scroll code applies the multiplier to EDIT_BUTTON_SCROLL_UP/
      DOWN_LINE regardless of whether the wheel or the keyboard produced
      it. So after a fast wheel burst, keyboard line scrolling may move
      several beats per press until the next wheel event, and the
      trailing-beat catch-up may stay boosted. Not tested; see check 4.
   b) Current speed not in the preset list [CODE]: the index search
      leaves iSpeed at 0 when the current scroll speed equals no preset,
      so the first step goes from the FIRST preset, not from the nearest.
      Same pattern in the Ctrl+Up/Down code. [INFERRED: what a player
      sees]
   c) Modifier keys are read directly from the keyboard (Ctrl/Shift), not
      through the edit mapping, so they cannot be remapped like other edit
      keys. [CODE]
 
6. Mouse drag selection [CODE: ScreenEdit::Input ~2933-2946, Update
   ~2264, DrawPrimitives ~2809, FinishMouseDragSelection ~2826,
   MouseYToBeat ~1824]
   - Left button press in the editing state starts a drag; a translucent
     blue rectangle (0.6,0.8,1.0 alpha 0.25) follows the cursor; release
     sets the area selection markers (the same begin/end markers as the
     keyboard "select area" and Shift+arrow methods).
   - Only the vertical extent matters; screen Y is converted to beats
     with the field's displayed (trailing) beat, so it matches what is
     drawn while scrolling.
   - Movement under 4 screen units vertically counts as a click and
     CLEARS the selection (both markers set to -1).
   - Normal drag: selection is tightened to the first and last note
     rows inside the rectangle; if there are no notes inside, the
     selection is cleared.
   - Shift + drag: bounds are quantized to the current snap (e.g. 16ths)
     instead of to notes, so empty regions can be selected.
   - If start row >= end row after this, selection is cleared. Plays the
     marker sound on success.
   - The wheel is separate: scrolling during a drag is not handled
     specially [UNVERIFIED for behavior; the rectangle uses fixed screen
     coordinates].
   - Any left click in the editing state (even one meant for the menu or
     elsewhere on screen) starts a drag and returns true from Input
     [CODE]; I did not check whether the edit screen has mouse-clickable
     elements that this would shadow. [UNVERIFIED]
   - Mouse coordinates are scaled from the window to theme coordinates
     using display height and aspect ratio preferences (GetMouseScreenX/Y)
     [CODE].

3. #464 - extern/ffmpeg/libavcodec/jpeg2000_parser.c:124 - cpp/unsigned-difference-expression-compared-zero
 [CODE] Line 124-125 (FFmpeg 9bc0bcce; identical on FFmpeg master at fetch time):
   m->skip_bytes = (state64 & 0xFFFFFFFF) - 9 > 0 ? (state64 & 0xFFFFFFFF) - 9 : 0;
   state64 is uint64_t, so the subtraction wraps for values 0..8 and "> 0" is false only for exactly 9.
   skip_bytes is uint32_t, so the wrapped value is truncated to about 4 billion.
 [INFERRED] The value is the 4-byte Psot (tile-part length) of a JPEG 2000 codestream. A corrupt or
   crafted file with Psot 0..8 makes the parser skip about 4 GB of input, so it stops finding frame
   boundaries. The skip loop is bounded by buf_size, so this is not a memory-safety bug. Psot = 0 is
   legal in the spec ("to end of codestream"), so one legitimate value triggers it.
 [CODE] The fork's FFmpeg configure flags (.github/workflows/ffmpeg-w32.yml) do not disable parsers;
   avcodec-59.dll contains "jpeg2000" strings, so the parser is probably built in. [INFERRED] ITGmania
   would only reach it by loading a deliberately malformed JPEG 2000 video as an asset.
 VERDICT: true positive in vendored code, no realistic impact. NOT FIXED. Dismiss as "won't fix:
 third-party". A fix would be (compare before subtracting):
   const uint32_t psot = state64 & 0xFFFFFFFF; m->skip_bytes = psot > 9 ? psot - 9 : 0;
 Better reported to FFmpeg than patched locally. [UNVERIFIED] whether already reported upstream.
 Other extern/ "unsigned difference" alerts are probably the same pattern (not read).

4. #461 - src/NoteDataUtil.cpp:1482 - cpp/uncontrolled-arithmetic ("uncontrolled data in arithmetic expression")
 [CODE] Shuffle/super_shuffle case (lines 1478-1485): int iShuffleSeed = GAMESTATE->m_iStageSeed;
   do { RandomGen rnd(iShuffleSeed); std::shuffle(...); iShuffleSeed++; } while (!memcmp(...)).
   m_iStageSeed is a plain int (GameState.h:138), set from rand() at GameState.cpp:326, 1237, 2557.
   RandomGen is MersenneTwister, ctor MersenneTwister(int iSeed = 0) (RageUtil/RandomNumbers.h).
 [INFERRED] ++ could overflow only if the seed is INT_MAX. On Windows (MSVC/MinGW) RAND_MAX is 32767,
   so it cannot happen; on glibc/macOS rand() could return INT_MAX with probability about 1 in 2^31,
   and the loop only runs when the first shuffle leaves the order unchanged. Signed overflow is
   technically undefined but in practice wraps, and the seed is not an index or size, so no memory
   corruption. Seeding from rand() is intentional (same shuffle for both players in a round). CodeQL
   treats any rand() source as "uncontrolled".
 VERDICT: false positive in practice. NOT FIXED. Dismiss. (Cheapest change if wanted: unsigned seed
 with a cast at the RandomGen call; not worth touching upstream code.) The same pattern is likely
 behind ArrowEffects.cpp:659, Course.cpp:537 and the soft-shuffle seed at NoteDataUtil.cpp:1513 if
 they are flagged later.

5. #427 - src/RageSurfaceUtils_Palettize.cpp:293 - cpp/new-free-mismatch (mismatching new/free or malloc/delete)
 [CODE] mediancut() allocates the colormap with malloc(sizeof(struct acolorhist_item) * newcolors)
   (line 324-325) and returns it; Palettize() stores it in acolormap (line 151) and released it with
   "delete acolormap;" (line 293). The other cleanups in that function are correct (pam_freeacolorhist
   uses free; thiserr/nexterr use new[]/delete[]).
 [INFERRED] Undefined behavior. acolorhist_item is a plain struct without a destructor and on MSVC,
   glibc and macOS operator delete reaches the same free(), so it works today. It would fail under
   debug-heap checkers (MSVC debug CRT, ASan, Valgrind report allocator mismatch) or with a custom
   allocator where new/delete and malloc/free use different heaps. Likely symptom: a crash or assertion
   while loading a texture that gets palettized, not a gameplay bug.
 FIX (applied): line 293 "delete acolormap;" -> "free(acolormap);  // allocated with malloc in mediancut()".
   free(nullptr) is safe, so the case where acolormap stayed nullptr still works. <cstdlib> is already
   included and free() is already used in the file (line 60).
 [CODE] Checked: same line, same malloc, on release and beta. g++ -fsyntax-only was run only on a
   stand-alone malloc/free snippet (the file itself was not compiled: it needs the project headers).
 STATUS: committed and pushed 2026-10-15 to the fork:
   release  51bf20206 -> d5f0548   beta  7b83223dd -> bd26dd6
